# Phase 05.1: Code Review Report

**Reviewed:** 2026-05-25T00:00:00Z
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

This phase replaces Vercel Blob with a Tigris S3-compatible bucket for icon storage. The migration
touches the icon upload library (`src/lib/icons.ts`), env-var validation in both sync entry points,
`next.config.ts` remote-pattern allowlist, and two one-off operational scripts. The core logic is
sound, but there are two blockers: live credentials committed to `.env.local` (which is checked in
and readable), and a SSRF bypass via redirect-following that defeats the fetch allowlist. Three
additional warnings cover an incorrect `revalidateTag` call signature, a missing null-guard on the
icon URL written to the DB, and the S3 client module being module-level (crashes the Vercel cold
start if env vars are absent). Two info items cover a content-type mismatch and the absence of error
handling if `PutBucketAclCommand` fails in the setup script.

## Critical Issues

### CR-01: AWS credentials committed to `.env.local`

**File:** `.env.local:5-6`
**Issue:** The `.env.local` file contains live `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`
values for the Tigris bucket. The file is present in the repo working tree and was read without any
`permission denied` error, which means it is not excluded by `.gitignore` or, if it is excluded,
there is a non-trivial risk it was accidentally staged. The values follow the `tid_…` / `tsec_…`
Tigris credential pattern and appear to be real production credentials, not placeholders. If this
file is — or was ever — committed, those credentials grant full write access to the public-facing
icon bucket and full S3 API access to whatever IAM policy the key holder has.

**Fix:**
1. Immediately rotate the Tigris access key and secret from the Tigris dashboard.
2. Verify `.env.local` is listed in `.gitignore` and has never been committed:
   ```bash
   git log --all --full-history -- .env.local
   git ls-files .env.local  # should return nothing
   ```
3. If it was committed at any point, purge it from git history with `git filter-repo` and
   force-push. Rotation alone is insufficient once a secret is in git history.
4. Replace the raw values with `REPLACE_ME` placeholders in a `.env.local.example` file if
   developer documentation is needed.

### CR-02: SSRF allowlist bypassed by redirect-following in `safeFetch`

**File:** `src/lib/fetch-allowlist.ts:20-26` (called from `src/lib/icons.ts:28`)
**Issue:** `safeFetch` checks the *initial* hostname against `ALLOWED_HOSTS` before the request is
made, then calls `fetch(url, { redirect: 'follow' })`. After following redirects, it only checks
whether the *final* hostname starts with a known private-IP prefix. It does NOT verify that the
final hostname is still in `ALLOWED_HOSTS`. A redirect from `icons.duckduckgo.com` to any arbitrary
external host — including other cloud metadata endpoints not covered by the CIDR prefix list (e.g.,
AWS EC2 metadata `169.254.169.254` is blocked, but `100.100.100.200` Alibaba metadata or any
attacker-controlled server) — would be followed and the response returned to the caller. The
icon buffer from that response is then uploaded directly to the Tigris bucket.

While the primary SSRF vector (private CIDR ranges) is partially mitigated, the post-redirect host
is not re-validated against the allowlist, so the allowlist provides no protection against open
redirects on allowlisted domains redirecting to arbitrary external hosts.

**Fix:**
```typescript
// After following redirects, verify the final URL is still on an allowed host
const response = await fetch(url, { ...init, redirect: 'follow' });
const finalHostname = new URL(response.url).hostname;

// Must still be an allowed host — not just a non-private address
if (!ALLOWED_HOSTS.has(finalHostname)) {
  throw new Error(`SSRF_BLOCKED: redirect target "${finalHostname}" not in allowlist`);
}
if (BLOCKED_CIDR_PREFIXES.some(p => finalHostname.startsWith(p))) {
  throw new Error(`SSRF_BLOCKED: redirect target "${finalHostname}" is a private address`);
}
return response;
```

## Warnings

### WR-01: `revalidateTag("casks", "max")` passes a cache *profile*, not a second tag

**File:** `src/app/api/cron/sync/route.ts:133`
**Issue:** The Next.js `revalidateTag` signature is:
```typescript
export declare function revalidateTag(tag: string, profile: string | CacheLifeConfig): undefined;
```
The second argument is an optional cache *profile* name (used with `use cache` / `cacheLife`
directives), not a second tag to revalidate. Calling `revalidateTag("casks", "max")` revalidates
the `"casks"` tag with a profile named `"max"`. If the intent was to also revalidate a `"max"` tag,
that does not happen. The same pattern appears in `src/app/api/revalidate/route.ts:11`.

If the codebase does define a `"max"` cache profile (e.g., via `cacheLife`) and that is the
intended second argument, the call is correct but the code looks like a mis-read of the API. If the
intent was two separate tag invalidations, the fix is:

**Fix:**
```typescript
// To revalidate only the "casks" tag (remove unintended profile argument):
revalidateTag("casks");

// OR, if both tags need revalidating:
revalidateTag("casks");
revalidateTag("max");
```

### WR-02: `icon_url: null` written to DB when S3 upload fails, silently hiding errors

**File:** `src/lib/icons.ts:46-48` / `src/app/api/cron/sync/route.ts:83`
**Issue:** When `fetchAndStoreIcon` returns `{ url: null, isFallback: true }` (either because the
DuckDuckGo fetch returned non-200, or because the URL parse failed), the cron pipeline writes
`{ icon_url: null, icon_is_fallback: true }` back to the DB. The `icon_url` stays `null`. On the
*next* sync run the icon pipeline re-queries `isNull(casks.icon_url)` and retries — that is
intentional and correct.

However, when `PutObjectCommand` throws (e.g., invalid credentials, network error, bucket
policy failure), the `catch` block in the sync loop swallows the exception and writes nothing
(the `db.update` inside the `try` is never reached). The row is retried next run. This is
acceptable for transient errors, but if credentials are wrong, every single sync run will silently
retry all ~17 K icons, burn through the 300 s Vercel timeout, and never make progress — with no
indication in the response body of what failed.

The `backend/src/routes/sync.ts` version logs the error via `logger.error`, which is better.
The Next.js cron version only `console.warn`s without any aggregate failure count in the response.

**Fix:**
```typescript
// In src/app/api/cron/sync/route.ts — track S3 errors separately
let s3ErrorCount = 0;
// inside the catch:
} catch (err) {
  console.warn("[cron/sync] icon failed for", c.token, err);
  if (String(err).includes('S3') || String(err).includes('credential')) s3ErrorCount++;
}
// include in response:
{ ..., icons_s3_errors: s3ErrorCount }
```
More importantly, ensure `AWS_ENDPOINT_URL` and credentials are validated before the icon loop
begins (they already are in the env-var check at line 21, so a misconfiguration will be caught
early — but only if that check runs before the loop, which it does).

### WR-03: S3 client instantiated at module load time; crashes cold start if env vars absent

**File:** `src/lib/icons.ts:6-14`
**Issue:** The `S3Client` is constructed at the top level of the module, outside any function, with
non-null assertions (`!`) on `process.env.AWS_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`, and
`AWS_SECRET_ACCESS_KEY`. If any of these env vars are absent, the SDK will not throw at construction
time (the AWS SDK stores credentials lazily), but `AWS_ENDPOINT_URL!` being `undefined` would be
passed as the endpoint. More critically, any code path that imports `src/lib/icons.ts` — including
pages and Server Components — will initialize the S3 client unconditionally. On Vercel preview
deployments without Tigris env vars set, this silently constructs a misconfigured client rather than
failing with a clear error, and the env-var guard in the cron route is the only protection.

**Fix:** Move the `S3Client` construction inside `fetchAndStoreIcon` or use a lazy initializer:
```typescript
let _s3: S3Client | null = null;
function getS3Client(): S3Client {
  if (!process.env.AWS_ENDPOINT_URL) throw new Error('AWS_ENDPOINT_URL is not set');
  if (!_s3) {
    _s3 = new S3Client({
      region: 'auto',
      endpoint: process.env.AWS_ENDPOINT_URL,
      credentials: {
        accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
        secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
      },
      forcePathStyle: false,
    });
  }
  return _s3;
}
```

### IN-01: `ContentType: 'image/x-icon'` used for all icons regardless of actual format

**File:** `src/lib/icons.ts:43`
**Issue:** The DuckDuckGo favicon service returns PNG images for most modern apps (not `.ico`
files), even when the URL ends in `.ico`. The object key is also named `${token}.ico`. Uploading a
PNG body with `ContentType: 'image/x-icon'` means browsers will receive the wrong MIME type, which
can cause rendering failures in some strict environments. The `next/image` optimizer may also
mishandle the content-type mismatch.

**Fix:** Inspect the `Content-Type` response header from DuckDuckGo and use it:
```typescript
const contentType = res.headers.get('content-type') ?? 'image/x-icon';
const ext = contentType.includes('png') ? 'png' : 'ico';
const key = `icons/${token}.${ext}`;
// ...
await s3.send(new PutObjectCommand({
  // ...
  ContentType: contentType,
}));
```

### IN-02: `set-bucket-policy.ts` has no error message if env vars are missing

**File:** `scripts/set-bucket-policy.ts:11-29`
**Issue:** All three env vars (`AWS_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`)
are accessed with `!` non-null assertions. If `.env.local` is absent or incomplete when the script
is run, the S3Client will be constructed with `undefined` values and the `PutBucketAclCommand` will
produce a confusing AWS SDK error rather than a clear "missing env var" message. Similarly, there is
no success-path verification that the ACL was actually applied.

**Fix:**
```typescript
const required = ['AWS_ENDPOINT_URL', 'AWS_ACCESS_KEY_ID', 'AWS_SECRET_ACCESS_KEY', 'AWS_S3_BUCKET_NAME'];
const missing = required.filter(k => !process.env[k]);
if (missing.length > 0) {
  console.error('Missing required env vars:', missing.join(', '));
  process.exit(1);
}
```
