    Create src/lib/icons.ts.

    Imports: put from '@vercel/blob', safeFetch from './fetch-allowlist'.

    Define constant DUCKDUCKGO_FAVICON = 'https://icons.duckduckgo.com/ip3'.

    Export async function fetchAndStoreIcon(token: string, homepage: string): Promise<{ url: string | null; isFallback: boolean }>.

    Implementation:
    1. Parse the homepage URL to extract the domain. Wrap new URL(homepage) in try/catch — if homepage is empty or invalid, return { url: null, isFallback: true } immediately.
    2. Set domain = new URL(homepage).hostname.
    3. Construct faviconUrl = `${DUCKDUCKGO_FAVICON}/${domain}.ico`.
    4. Call res = await safeFetch(faviconUrl). This goes through the SSRF allowlist which includes 'icons.duckduckgo.com'.
    5. PITFALL: DuckDuckGo returns a PNG body on BOTH 200 and 404. Check res.status !== 200, NOT body length or content type. If res.status !== 200, return { url: null, isFallback: true }.
    6. Read iconBuffer = await res.arrayBuffer().
    7. Call blob = await put(`icons/${token}.ico`, iconBuffer, { access: 'public', contentType: 'image/x-icon', allowOverwrite: true }). The @vercel/blob SDK reads BLOB_READ_WRITE_TOKEN from process.env automatically.
    8. Return { url: blob.url, isFallback: false }.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cron route → icons.duckduckgo.com | Favicon fetch for each cask homepage domain — redirects may lead to untrusted hosts |
| icons.duckduckgo.com response → Vercel Blob | Raw binary (arrayBuffer) uploaded to Blob — content is user-controlled if homepage points to attacker domain |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure / SSRF | DuckDuckGo favicon fetch | mitigate | safeFetch() validates both the initial URL and post-redirect URL against ALLOWED_HOSTS and BLOCKED_CIDR_PREFIXES; DuckDuckGo redirecting to private IPs is blocked by the redirect chain validator in fetch-allowlist.ts |
| T-03-02 | Tampering | Malicious icon content uploaded to Vercel Blob | accept | Icons are stored as binary and served as images; Vercel Blob serves them with correct content-type; no code execution risk. Worst case: a wrong icon is displayed for a cask. |
| T-03-03 | Denial of Service | 7,659 concurrent Blob upload operations | mitigate | Concurrency capped at 10 (chunks of 10 via Promise.all); Vercel Blob Pro tier supports 75 ops/sec; 10 concurrent requests stays well within limits |
| T-03-04 | Information Disclosure | BLOB_READ_WRITE_TOKEN logged in error output | mitigate | Catch blocks log String(err) without including env var values; token is accessed via @vercel/blob SDK internally (not in application code) |
| T-03-SC | Tampering | npm/pip/cargo installs | mitigate | @vercel/blob 2.4.0 verified in Package Legitimacy Audit in RESEARCH.md; disposition=Approved |
</threat_model>
